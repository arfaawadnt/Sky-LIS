Status after the fixes (v1.1): all 49 findings fixed and verified

All 49 findings of this validation were fixed in three rounds and verified on screen, in the database and by tests. Every finding raised while re-testing the fixes was fixed too, including one regression the fixes caused. Section 10 has the detail. The suites grew from 1,589 to 1,869 automated tests, all passing, and the backend cycle passes 36 of 36 steps on the fixed build. The two session defects of severity 1 are closed: a tab can no longer act as another user, and nothing of a previous user survives a sign-out.

One item is left open on purpose. B-09 (CSV format) is fixed on every Release-1 page, but the export of the hidden Release-2 page "sending labs" still writes payer ids.

Original verdict (v0.3.8): functionally and data-wise validated — two session defects must be fixed before shared-workstation use

Every Release-1 business workflow of both portals works end to end, every business rule tested is enforced by the server, and every save checked reached the database with the right values, tenant, links, audit entries and processed outbox events. No data loss or data corruption was found in the backend, and tenant isolation held at the API and at the database row level.

The defects are in the browser application. Two are severity 1 and both concern two users sharing one browser: after a sign-out and sign-in, some pages keep the previous user's data (A-01), and a forgotten tab can continue as the user who signed in last (C-01). Five severity-2 defects lose user input or mis-report a successful save. The recommendation is to fix the S1 and S2 groups (section 6), re-test them, and then open user acceptance with the personas.

1. Scope and method

  • Automated layer. The full solution build and the five backend suites (domain, architecture gates, application, integration on a real PostgreSQL, functional through the real API and database), the frontend lint with module boundaries, the frontend unit tests and the production build.
  • Manual layer, page by page. Four testers covered every Release-1 menu entry of both portals (26 client, 33 Super Admin) and the public pages: every list (search, filters, sort, paging, export), every editor (create, edit, validation messages, activate and deactivate), every row action and dialog, the keyboard shortcuts, the permissions of each persona, and the Arabic right-to-left view of each page. Expected results came from the business SRS (LIS-SRS-001), the module intakes and the UAT scripts (LIS-UAT-001 v0.4).
  • Backend cycle. After every save on a screen the tester queried the database read-only: the row in the right table with exactly the entered values and tenant, the child rows, the audit trail and field changes, and the processing of the transaction's outbox events. A fifth tester built a repeatable script that drives the API directly through a complete laboratory cycle and asserts the database after each request, including the negative and isolation checks.
  • Release-1 scope only. Release-2 pages hidden by the release switch were not tested. Nothing was changed in the application during the validation; every defect is recorded with its suspected cause instead.

4. Business rules confirmed

  • Registration and money: duplicate and gender-restricted services, reserved lines, discount cap and mandatory reason, partial payment, non-cash reference, payment above the remaining balance refused, payment only on a treasury approved for the device, refund limited to the refundable amount, cancellation with reason, verified lines cannot be cancelled.
  • Results: entry only on received samples, flags and panic values against the age and sex band, formula computation, list and text tests, delta acknowledgement, verify refused with missing values, review-before-verify when enabled, amend only with the special right and a reason, result rights per clinical group and branch.
  • Segregation of duties: a treasury access requester cannot approve their own request (SOD-TRS-001).
  • Organization and security: live permission change (BR-17), branch selection, must-change password gate, lockout after five failures, lock and unlock, deactivated client refused at sign-in (CLI-020), password policy inherited from the platform parameter.
  • Catalogue and pricing: unique codes (CAT-0xx), BR-19 affordances, price list copy with factor, contract tiers (PRC-0xx), master-data copy to new clients (BR-25).
  • Isolation: tenant isolation at the API (404 across laboratories) and in the database (row-level security), client feature routes closed to platform sessions, /admin closed to laboratory sessions.

Findings raised by the re-tests, all fixed

  • R1-01 (S2, regression): the refund page was marked Release 2, so the new guard refused the refund action. Pages reached only from an action now carry menu: false in the registry, and a spec checks every Release-1 action target.
  • Security hardening: sign-out and sign-in now act only on a refresh cookie whose secret matches. A sign-in ends the browser's previous session, and a forged or stale cookie ends nothing.
  • Smaller items:
    • delayed-tests table, with its due time;
    • other tabs follow a password change;
    • the client home sends each user to a page they may open;
    • Release-2 actions, tiles and landing texts hidden;
    • country and governorate exports filtered;
    • Arabic options in the report-template dialog;
    • a read-only visit view and a read-only template view for users without edit rights;
    • the visit summary nets refunds;
    • no internal laboratory id on the profile;
    • one export notice and local file names;
    • a refusal notice for the portal guards.
