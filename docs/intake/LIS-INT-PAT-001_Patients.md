## 1. Purpose and policy basis

The **patient file** is the permanent identity of a person in one laboratory (tenant): every visit, sample, result and
payment hangs off its number (LDM §3.1, synthesis §2.1). The number is generated by the system and **never changes**
(BR-01). Reference ranges resolve by sex, age and patient condition (BR-08, LDM §3.5), so sex and age are part of the
file. Duplicate files are the main data-quality failure of the legacy system (synthesis §13: manual numbers, hasty
"New Patient", no merge); Sky LIS therefore (a) warns about similar existing files while the clerk types a name and
mobile (REG-002, LDM §4.3), (b) searches by number, name, mobile or national id before typing, and (c) lets a holder of
the merge right merge two files into a surviving one with an audited reason (REG-003, CP-11 "merge duplicates
(right)"). Attached documents (referrals, IDs, previous reports) are kept with the file, visible from every branch
(CP-11; the legacy system did not replicate attachments, synthesis §8 / §13), and never erased (BR-15).

## 2. Scope and out of scope

In scope:

- Patient file life cycle: register (T1), update demographics (T2), merge a duplicate into a survivor (T3).
- Documents: attach (T4, pdf/jpg/png ≤ 10 MB), list, download, deactivate with a reason (T5; no delete, BR-15).
- Registers: patient search/list with filters and CSV export; patient detail; similar-patient candidates (BR-01 /
  REG-002); the tenant parameters a patient form needs (mandatory mobile / national id, similar-name warning).
- Read port `IPatientLookup` for Registration and Results (summary by id and by ids).
- Shared file storage port `IFileStore` + `LocalFileStore` (other modules reuse it for attachments).
- UI: patients list (CP-11), create/edit drawer, patient page (tabs File / Documents / Visits), merge dialog, and the
  reusable **patient picker** (search → similar warning → "use this file" → inline create) that Registration (CP-06,
  next wave) embeds.

Out of scope (other modules or later intakes):

- Visits history content (Registration, wave 2): the Visits tab calls `GET /api/v1/registration/visits?patientId=`
  and shows an empty state until that endpoint exists. Visit count / last visit columns of CP-11 arrive with the
  same module.
- Moving visits, results and payments to the surviving file: policies of Registration, Results and Billing on
  `PatientsMerged` (CP-11 rule "merge moves visits, results and payments to the surviving file").
- Search by accession (REG-002 lists it): the Registration module's search (CP-10).
- Un-merge (no reversal transition; see §16 Q4), patient portal / result delivery by e-mail, SMS.
- Country-specific mobile length on the server (the client applies it when `/api/v1/platform/countries` publishes
  lengths; the server enforces 8–15 digits).

## 5. Aggregates

- **Patient** (root, `app.patients`): `Number`, `Title`, `FullName`, `NameAr?`, `NameKey`, `NameArKey?`, `Gender`,
  `DateOfBirth?`, `AgeYears?/AgeMonths?/AgeDays?`, `RegisteredOn`, `PatientConditionId?`, `Mobile?`, `NationalId?`,
  `Nationality?`, `Email?`, `GovernorateId?`, `City?`, `Address?`, `Comments?`, `IsVip`, `Status`,
  `MergedIntoPatientId?`, `MergedAtUtc?`, `MergedByUserId?`, `MergeReason?`, `RowVersion` (xmin) + audit stamps.
  Value logic: `PatientAge` (years/months/days between two dates), `PatientNameNormalizer` (search keys and token
  comparison), `PatientTitles` (default gender).
- **PatientDocument** (root, `app.patient_documents`): `PatientId` (composite FK to the patient), `FileName` (display
  only), `ContentType` (detected, not the client's), `SizeBytes`, `StorageKey` (server-generated), `Sha256`, `Note?`,
  `UploadedByUserId`, `UploadedAtUtc`, `IsActive`, `DeactivatedByUserId?`, `DeactivatedAtUtc?`, `DeactivationReason?`.
  Its own aggregate because a file's documents grow without bound and change independently of the demographics
  (03 §3 step 4); the only cross rule (attach only to an Active file) is checked at attach time.

## 9. Segregation-of-duties rules

None. Registering, editing and merging are single-actor reception/administration acts; the merge is protected by
its own permission (`patients.manage`), a mandatory reason and the audit ledger. (Assumption Q5: no
"creator ≠ merger" rule.)

## 10. Approval gates

None. The merge is irreversible but executed by a holder of `patients.manage` after a danger confirmation in the UI;
step-up re-authentication is not required (assumption Q6; the configuration hook of 02 §4.5 can list the merge later).

## 11. Events and policies

```text
Event:    PatientRegistered { PatientId, Number, Gender, OccurredAtUtc, TenantId }
Raised by: T1
Reacts:   none yet (hook for a patient portal / notifications intake)

Event:    PatientUpdated { PatientId, Number, OccurredAtUtc, TenantId }
Raised by: T2 (only when a field changed; the field history is in audit.field_changes)
Reacts:   none yet

Event:    PatientsMerged { SurvivorId, SurvivorNumber, MergedId, MergedNumber, ActorUserId, Reason, OccurredAtUtc, TenantId }
Raised by: T3 (on the merged file)
Reacts:   Registration — "when merged, then re-point the merged file's visits to the survivor" (idempotent on (VisitId, SurvivorId))
          Results / Billing — "when merged, then re-point results / payments of those visits" (idempotent on the row id)   [later waves]
Timing:   within one outbox cycle (seconds)

Event:    PatientDocumentAttached { DocumentId, PatientId, ContentType, SizeBytes, OccurredAtUtc, TenantId }      Raised by: T4   Reacts: none
Event:    PatientDocumentDeactivated { DocumentId, PatientId, ActorUserId, Reason, OccurredAtUtc, TenantId }     Raised by: T5   Reacts: none
```

Events carry ids, the numbers and the reason, never names or contact details (PII stays out of the outbox and the
ledger payloads). Documents are **not** moved by the merge: the documents register of a survivor lists its own
documents plus those of every file merged into it (transitively), each tagged with its original file number, so the
provenance is kept and no outbox delivery is needed (§16 Q7).

Name normalisation for search and similarity (`PatientNameNormalizer`, unit-tested): Unicode decomposition with
diacritics removed (Latin accents, Arabic harakat, superscript alef), tatweel removed, alef forms (أ إ آ ٱ) → ا, yaa
forms (ى ی ئ) → ي, ؤ → و, taa marbuta ة → ه, lower case, punctuation → space, titles stripped (mr, mrs, miss, ms, dr,
master, baby, prof, السيد, السيده, الانسه, د, دكتور, الدكتور, ا.د, استاذ, الطفل, رضيع …), compounds joined (`عبد ال…` →
`عبدال…`, `abdel rahman` / `abd el rahman` → `abdelrahman`), spaces collapsed. Two names **match** when their keys are
equal, or when they share at least two tokens and the shorter name's tokens are all contained in the longer one (order
free). Candidates: `Exact` = name match and same mobile; `Mobile` = same mobile; `Name` = name match; Active files only,
at most 10, ordered Exact → Mobile → Name → newest.

Open questions (assumed answers let the build proceed; confirm or change):

| # | Question | Assumed answer |
| --- | --- | --- |
| Q1 | Is a date of birth or an age mandatory? (Sky prototype: DOB*, LDM: sex mandatory, birth date ↔ age) | Yes: one of them is required, because ranges depend on age (BR-08). |
| Q2 | Does the title force the gender? | No: it sets the default in the UI; the server accepts any combination (e.g. "Dr", "Baby"). |
| Q3 | Should a national id be unique per tenant? | No uniqueness: a duplicate national id is surfaced by search and resolved by merge; a hard refusal would block registration on a data-entry error in the other file. |
| Q4 | Can a merge be undone? | No reversal transition in this version (the record of the merge is permanent, BR-15); a wrong merge is corrected by registering a new file. |
| Q5 | SoD on merge (creator of a file ≠ merger)? | None. |
| Q6 | Step-up re-authentication for the merge? | Not required. |
| Q7 | Are documents moved to the survivor on merge? | Not moved: the survivor's register shows them with their original file number (provenance kept). |
| Q8 | Must VIP files be hidden entirely from users without the VIP right (LDM rights `Vip`, `Print Vip`)? | **Aligned with REG Q12 — assumption, awaiting the business owner (validation A-03, 2026-10-11).** Not hidden, masked: for a user without the See-VIP special right (`SpecialRights.CanSeeVip`, CP-37, the right the visit register uses) a VIP file is listed in the patient register (CP-11), its CSV export, the patient picker and the similar-file check without its name, Arabic name, mobile and national id (the export also drops e-mail and address); name, mobile, partial-number and partial-national-id searches never match it; the full patient number or the full national id still finds it (masked) so reception can register the patient.
