Part A

Current development

What has been built, how it was verified, and where it runs — as of release v0.14.1 (2026-10-14) plus change request LIS-CR-003 of 2026-10-19, built and verified in the repository and awaiting its release (v0.15.0) and installation.

2. Product shape and architecture

Sky LIS is a cloud, multi-tenant laboratory information system with two portals on one backend: the Client Portal used by each laboratory (reception, laboratory, finance, set-up, account) and the Super Admin Portal used by National Technology (clients, subscriptions, master data, platform). A laboratory subscribes on the public site, verifies the manager's mobile and receives a fully provisioned tenant with the global catalogue copied in.

Backend

  • .NET 9 / C# 13, Clean Architecture in six projects (Platform.*), CQRS with MediatR, FluentValidation, EF Core 9 on PostgreSQL 17.
  • Tenant isolation by composite keys (tenant_id, id) and PostgreSQL row-level security on every tenant table; the runtime role cannot bypass it.
  • 27 API controllers, about 500 operations under /api/v1; 96 tables in 15 migrations; one idempotent deployment script.
  • Every command and query carries a permission policy; architecture tests enforce the layer rules, the policy rule, atomic transitions and the migration script freshness.

Frontend

  • Angular 22 (zoneless, signals), strict TypeScript 6, Vitest; 79 pages on a shared UI kit (tables with server-side paging and sorting, drawers, dialogs, tabs, print documents).
  • English and Arabic (RTL) on every page; language and results density saved as user preferences.
  • Release scope switch (RELEASE_SCOPE = 'R1'): Release-2 pages exist behind it and are hidden from menu and routes.
  • Session rules proven in validation: one identity per tab, cross-tab sign-out, idle timeout with warning, branch of the session.

4. Platform foundations delivered

Security

  • Credential envelope (the browser seals passwords and codes with a per-request key), Argon2id hashing, ES256 access tokens of 15 minutes, encrypted subject identifiers.
  • Refresh-token rotation with reuse detection and family revocation, strict cookie scope, origin and CSRF checks, rate-limit matrix per endpoint.
  • Password policy and forced change, mobile numbers in E.164 and unique in every spelling, idle timeout per tenant, one identity per browser tab.
  • Start-up guards refuse a non-LIS database, foreign configuration keys and relaxed security in production.

Audit and operations

  • Field-level change log, hash-chained audit trail per tenant with a verify-chain endpoint, security-event ledger; all append-only at database level.
  • Transactional outbox with a hosted processor, lease, back-off and dead letter; domain policies react to events (visit registered, sample collected, patients merged …).
  • Notifications over SMS gateway, SMTP or a pickup folder; templates editable on the admin portal with built-in fallback.
  • Windows service and IIS site installers, verified backups, restore drills, smoke test, runbook and installation records.

9. Method and scope of the comparison

The two files supplied on 2026-10-18 are supersets of the earlier prototypes: the v3 client keeps everything v1 had and adds layers labelled v2, v2.1 and v3 (patches on the navigation, the dictionary and the pages); the v4.1 admin keeps the v2 screens and reworks the catalogue. The comparison therefore treats the delta as the proposal. Each prototype was inventoried structurally (navigation, pages, fields, buttons, grids, validation texts, dictionary patches), diffed against its predecessor, and every resulting proposal was checked against the built code — domain model, API contracts, routes and pages — not against documents.

12. Built, but absent from the prototypes

The developed application covers the whole Release-1 scope of the Business SRS and a number of later decisions that the v3 / v4.1 prototypes do not show. Adopting the prototypes literally would remove them; the recommendation is to keep every item below.

  • Treasury (CP-28 / CP-29): treasuries per branch, device-bound access requests, approval with segregation of duties and the primary-administrator exception, revocation; cash accepted only on an approved treasury (BR-27).
  • Payments register and refunds (CP-23), the collections report by method / cashier / branch with the branch right; cash closing (Release-2 backend).
  • Work amount report with eight groupings, CSV and the per-user report-days limit.
  • Special rights (discount cap, pay, refund, transfer, cancel, modify verified, preview unverified, print invoice, see VIP, demographics edit limit, branch collections, report days) and result rights per clinical group × branch.
  • Patient identity lock by result status and VIP masking.
  • Results by accession as built: sticky context strip, criteria dialog, matching-visits panel, previous / next visit, review → verify with delta acknowledgement, amend with reason, undo, comments and internal notes, print lists, report templates with logo and signature, hidden-by-rights notes.
  • Audit: field changes, hash-chained audit trail, security events, verify-chain endpoint, audit log pages.
  • Platform: subscriptions and wallets (plans, charge run), notification templates, platform parameters, sessions, 26 tenant settings including time zone and session timeout.
  • Security: credential envelope, refresh-token rotation with reuse detection, idle timeout, password policy, mobile uniqueness, rate limits, row-level security per tenant.
  • Catalogue extras and Release-2 backends: patient conditions, reasons, diagnoses, additional services, report templates, test rules, shortcut sets, sending labs, doctors; analysers, site agents, PCR kits, verification settings, medical rules.
